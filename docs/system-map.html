Loan Matcher — System Map

How the data, APIs, frontends and login roles connect. Traced from source on 2026-10-01. Companion to context.md (the why) and README.md (the how to run).

1. What the tool is

A sales-rep screen used live on a phone call. The rep fills a short intake rail; 49 SBA lender programs re-rank on every keystroke as strong / potential / poor / ineligible. The rep can open a program (talk track, why-it-fits, watch items, rep-only thresholds), compare up to four side by side, and model affordability with a payment slider. Output to the customer is an email draft (mailto:), never an application. Each send is logged so sales managers can see what gets recommended and compared.

3. Layer by layer

Sources → boot

  • src/instrumentation.ts runs on server start, calls ingestCsv in src/db/ingest.ts. The CSV is hashed (sha256). Unseen hash → new snapshots row and 49 normalized lender_programs rows inside one transaction. Seen hash → "exists", nothing written. Old snapshots are kept.
  • An unknown special_requirements phrase throws with the phrase in the message, so a human maps it to a rule_key in SPECIAL_KEYS before the data is trusted.
  • src/db/client.ts opens data/app.db lazily on first use (WAL, foreign keys on) and runs the Drizzle migrations. Migration 0001 creates the login and traction tables and seeds 8 SDRs + 2 managers; 0002 sets every password to password.
  • Both pages also call ingest inline if a request arrives before boot finished, so the app never serves an empty snapshot.

SQLite — three table families

FamilyTablesKey semantics
Rate sheetsnapshots, lenders, program_types, business_types, special_requirements, lender_programsFact rows carry snapshot_id; the app serves the latest. max_debt_ratio NULL = no rule listed. business_type_id NULL = All.
Loginsusers, sessionsusers.role = sdr | manager gates every manager path. sessions.id is a random 32-byte token and is literally the cookie value; 30-day expiry.
Tractionrecommendations, recommendation_programsOne row per email draft opened (kind = proposal | comparison, customer name + email, time). Junction pins the exact lender_programs.id. "Compared with" is a self-join on the junction. Aggregation groups by lender + program type so totals survive re-imports.

Next.js server — pages

  • Every page and API starts the same way: read the session cookie → userFromToken in src/db/auth.ts → decide.
  • / (SDR app): no user → redirect /login. Loads the full latest snapshot server-side and passes programs, snapshot, user as props to <App>. The browser never fetches programs.
  • /manager: no user → /login; SDR → /. Renders <ManagerApp> with the snapshot summary only; traction data is fetched client-side.
  • /login: client form with a hard-coded username list (mirrors the seed). POST → cookie → router.push by role.

SDR browser

  • src/components/App.tsx is the hub. useIntake (a tiny useSyncExternalStore over localStorage key newity.intake.v3) gives the intake; programs.map(evaluate).rank(preset) runs in one useMemo. That single ranked array feeds the intake rail (for "Unlocks X" hints), the match list, and the compare view.
  • Rules, tiering, best-fit score, amortization and all copy are pure functions in src/lib/ (rules.ts, rank.ts, money.ts, copy.ts). Zero network per keystroke.
  • Compare set is the rep's pinned ids, limit 4, filtered against ranked; a program that turns ineligible drops out silently. Selecting a column drives the affordability slider.
  • The only server write during a call: a MailLink click opens mailto:, copies the same draft to the clipboard, and POSTs to /api/recommendations with keepalive. "Email proposal" logs a proposal; "Send comparison" logs a comparison (one column → proposal).

Manager browser

  • ManagerApp holds month + rep filters, fetches /api/traction on every change, and redirects to /login on a non-OK response. Month defaults to the current month; "All time" is offered.
  • TractionTable is pure render: ranked bars (compared vs solo width relative to #1), top 8 with "show all", and a row click revealing "Most compared with", "Most recommended by" and "Last sent".

The loop

SDR send → traction tables → manager view. Snapshot date / counts appear in both top bars from the same loadPrograms call. Log out from either role posts to the same endpoint.

  2. Rules — boundary cases per hard rule and per rule_key; tier precedence (hard fail → soft fail → unknown → strong). money.test.ts.

  4. Roles — redirects on / and /manager; landing page by role; cookie flags.
  5. Frontends — type intake → re-rank, open card, compare 3–4, slider, send → row appears in manager view; refresh keeps intake.
